Institute / Department / Faculty Schema

Visual blueprint for the new platform. It keeps departments independent in their daily work while allowing a correct institute-wide collective view.

The important design choice

Do not create separate physical tables such as cse_publications, ece_publications, and a copied all_publications. That creates duplicate data and wrong totals. Use one clean boilerplate schema; every department-owned row is scoped by department_id, and the collective is built from canonical records and read-only roll-up views.

Department-owned data

Rows, not duplicate tables

Faculty appointments, CMS, programmes, labs, equipment, students, placement records and research attribution are owned by a department through department_id.

Canonical research

Create once

A publication, patent or project exists once. Ordered author/member links attach it to people and department-attribution links attach it to every relevant department.

Collective read model

Calculate, never copy

Materialized views calculate public counters and rankings. A CSE–ECE publication appears on both department pages but counts once at institute level.

Combined table: what the institute actually reads

The collective should use views/materialized views, not copied operational tables.

Read modelBuilt fromPurpose and de-duplication rule
v_department_kpisdepartment attribution + approved canonical research + current appointmentsOne row per department/year. A shared publication is intentionally visible to each participating department.
v_institute_kpisapproved publications, projects, patents, faculty snapshotsOne row per institute/year. Counts DISTINCT publication.id and DISTINCT project.id, so cross-department work is not double-counted.
v_faculty_kpisfaculty author/member links + latest source metric snapshotsOne row per faculty/year/source. Powers individual portfolio cards and faculty rankings.
v_research_cataloguepublished research + author/department linksSearchable public catalogue filtered by JOURNAL, CONFERENCE, BOOK, or BOOK_CHAPTER.

Complete department database table catalogue

How to read this catalogue

Each row below describes the shape of one database table: what one database row means, its key columns, and its links. Every mutable base-table row also carries id UUID PK, created_at, trigger-maintained updated_at, deleted_at NULL, created_by, and updated_by, even where those boilerplate columns are not repeated. Join tables use their own UUID key and preserve relationship metadata such as order or role. Append-only history tables retain timestamps but are not soft-deleted.
